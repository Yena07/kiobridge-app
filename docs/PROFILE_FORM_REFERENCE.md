# 프로필 입력 폼 — 다른 곳은 어떻게 받나

우리 폼을 고치기 전에, 같은 문제를 오래 풀어 온 곳들이 무엇을 정해 두었는지 모았다.
셋을 봤다.

- **GOV.UK Design System · Service Manual** — 영국 정부의 모든 서비스가 쓰는 폼 규칙.
  전 국민이 쓰는 서비스라 "컴퓨터에 익숙하지 않은 사람" 이 기본 사용자다. 우리와
  사용자층이 가장 비슷하다.
- **W3C WAI — Older Users** — 고령 사용자를 위한 웹 콘텐츠 지침.
- **KWCAG 2.2** — 한국형 웹 콘텐츠 접근성 지침(국가표준). 심사에서 근거로 쓸 수 있는 것.

아래 표의 판정은 **우리 코드를 직접 확인한 결과**다. 짐작이 아니다.

---

## 1. 한 화면에 하나만 묻는다 (One thing per page)

GOV.UK 가 폼 구조에서 첫 번째로 두는 규칙이다. 한 화면에 질문 하나 — 정보 하나,
결정 하나, 질문 하나.

왜 그렇게 하나(GOV.UK 가 드는 이유):

- 무엇을 묻는지 이해하기 쉽다
- 한 번에 한 가지에만 집중하면 된다
- 처음 겪는 절차를 헤매지 않는다
- 작은 화면에서 쓰기 좋다
- **틀렸을 때 어디를 고쳐야 하는지 바로 안다**

### 우리는

| 화면 | 지금 | 판정 |
|---|---|---|
| 가입(1/3) → 호칭(2/3) → 도움 설정(3/3) | 단계마다 하나씩 | **맞음** |
| 주문표 만들기 | 메뉴 이름 · 장소 · 세부 옵션 · 가격 한도 · 메모 를 **한 화면에** | 어긋남 |

주문표 만들기가 이 규칙에서 가장 멀다. 다만 이건 "고쳐야 할 버그" 가 아니라
**맞바꿈**이다 — 한 화면에 모으면 훑어보고 고치기 쉽고, 나누면 한 번에 하나만
보면 된다. 이미 저장된 주문표를 다시 열어 고치는 길이 없다는 점(아래 4번)까지
같이 보고 정할 문제다.

---

## 2. 안 물어도 되는 것은 안 묻는다 (Question protocol)

GOV.UK 는 폼을 만들기 전에 **질문 목록을 문서로 정당화**하게 한다. 질문마다
이렇게 답할 수 있어야 한다 — 왜 필요한가, 어디에 쓰는가, 누가 답해야 하는가,
정확한지 확인할 수 있는가, 안전하게 지킬 수 있는가.

이름에 대해서는 더 구체적이다.

> 서비스를 제공하는 데 필요할 때만 이름을 묻는다.
> **호칭(Mr/Mrs 같은 것)은 묻지 말라** — 성별과 혼인 여부를 드러내게 하는 일이고,
> 어떤 호칭이 있을지 미리 다 알 수도 없다.

### 우리는

**여기는 우리가 더 엄격하다.** 실제 이름을 아예 안 받는다.

- 화면이 묻는 것은 "부를 호칭" 이고, `실제 이름 말고, 불리고 싶은 말을 적어 주세요` 라고 안내한다
- 열두 자로 잘라 주소·전화번호가 들어갈 수 없게 했다
- `canonical.ts` 어디에도 안 들어가고 서버로 나가지 않는다. `sessionStorage` 에만 있다
- 메모 칸 옆에서 무엇을 적지 말아야 하는지 밝히고, 전화번호·주민등록번호 모양을
  걸러 낸다

GOV.UK 는 `autocomplete="name"` 을 권하지만 **우리는 일부러 `off` 다.** 브라우저
자동완성이 진짜 이름을 채워 넣으면 "이름은 받지도 저장하지도 않아요" 라는 약속과
정반대가 된다. 규칙을 어기는 게 아니라, 규칙이 전제하는 상황(진짜 이름을 받는 폼)이
우리와 다르다.

---

## 3. 라벨은 칸에 묶는다

KWCAG 2.2 와 WCAG 모두 같은 말을 한다.

> 사용자 입력에는 그 용도를 이해할 수 있는 **레이블을 제공**해야 한다.

`aria-label` 만으로도 스크린리더는 읽는다. 그런데 **눈으로 보는 사람에게는 아무
효과가 없다.** 진짜 `<label htmlFor>` 로 묶으면 라벨 글자를 눌러도 칸에 커서가
간다 — 손이 떨리는 분에게는 누를 수 있는 자리가 두 배로 넓어지는 일이다.

### 우리는 — **섞여 있다**

| 자리 | 지금 |
|---|---|
| 가격 한도 | `<label htmlFor>` + `aria-describedby` · **맞음** |
| 아이디 · 비밀번호 | 공용 입력 컴포넌트가 `id`/`label` 를 묶음 · **맞음** |
| 호칭 | `<label htmlFor="name-input" className="sr-only">` · **맞음** |
| **메뉴 이름** | 보이는 글자는 `SectionLabel`(그냥 글), 칸에는 `aria-label="메뉴 이름 (필수)"` · **안 묶임** |
| **메모** | 같은 모양 · **안 묶임** |

메뉴 이름과 메모 두 곳이 남았다. 고칠 거리가 작고(`SectionLabel` 에 `htmlFor` 를
받게 하고 칸에 `id` 를 주면 된다), 얻는 것은 분명하다.

덤으로 하나 더 — 지금은 보이는 글자("메뉴 이름")와 읽히는 글자("메뉴 이름 (필수)")가
**따로 적혀 있다.** 한쪽만 고치는 날이 오면 눈과 귀가 갈린다. 묶으면 그 위험이
사라진다.

## 4. 보내기 전에 답을 다시 보여 준다 (Check answers)

GOV.UK 의 별도 패턴이다. 제출 직전에 **답을 모아 보여 주고, 항목마다 '고치기'
링크**를 둔다. WAI 의 고령 사용자 지침도 같은 것을 요구한다 — 확정 전에 검토하고
고칠 수 있어야 한다.

### 우리는

**승인 직전은 맞다.** 확인 카드가 실제 상품명·포장·매운맛·종이컵·가격을 보여 주고,
그걸 보고 승인한다. 심사 규칙이 요구하는 다섯 가지 그대로다.

**저장된 주문표는 아니다.** 한 번 만든 주문표를 다시 열어 고치는 길이 없다.
지우고 새로 만드는 것뿐이다. 팀 #96 리뷰에서도 같은 지적이 나왔다 —
"`OrderSheetScreen` 에는 저장된 주문표 편집 기능이 없습니다".

**이 문서를 만들면서 확인한 것 중 가장 실질적인 구멍이다.**

## 5. 오류는 무엇이 잘못됐고 어떻게 고치는지 말한다

WAI 고령 사용자 지침:

> 오류 메시지는 **눈에 띄고 이해할 수 있어야** 하며, 가능하면 **어떻게 고치는지**
> 함께 알려 준다.

KWCAG 도 같다 — 입력 오류를 수정하는 방법을 텍스트로 자세히 제공하는 것이
학습장애가 있는 사용자에게 도움이 된다.

### 우리는 — 맞는 편이다

```
전화번호·주민등록번호·주소처럼 보이는 것이 있어요. 지워 주시면 저장할 수 있어요.
맨 위 메뉴 이름을 적으면 저장할 수 있어요
같은 비밀번호를 한 번 더 적어 주세요
```

무엇이 문제인지와 무엇을 하면 되는지를 같이 말한다. `role="alert"` 로 소리로도 간다.

GOV.UK 는 여기에 더해 **화면 맨 위에 오류 요약**을 두고 해당 칸으로 건너뛰는 링크를
붙인다. 우리는 한 화면에 칸이 한두 개뿐인 화면이 많아 그만큼의 값어치는 없다.
다만 주문표 만들기처럼 칸이 여럿인 화면에는 쓸모가 있다(1번과 같이 볼 문제).

---

## 6. 필수와 선택 중 무엇을 표시하나

GOV.UK 는 **선택 항목에만** "(optional)" 을 붙인다. 대부분이 필수라서, 필수에
별표를 붙이면 화면이 별표로 뒤덮인다.

### 우리는 — 반대인데, 우리 쪽이 맞다

주문표 만들기에서 **필수는 메뉴 이름 하나**고 나머지는 다 선택이다. 이럴 때는
필수를 표시하는 편이 표시가 적다. 지금 `필수`/`선택` 을 둘 다 붙이고 있는데,
둘 다 붙이는 것 자체는 잃을 게 없다 — 어느 쪽이 어느 쪽인지 헷갈릴 일이 없어진다.

## 정리 — 해 볼 만한 것

작은 것부터.

1. **메뉴 이름·메모 라벨을 칸에 묶기** — `SectionLabel` 에 `htmlFor`, 칸에 `id`.
   보이는 글자를 눌러도 커서가 가고, 보이는 글자와 읽히는 글자가 하나가 된다.
2. **저장된 주문표 고치기** — 지우고 다시 만드는 것 말고 여는 길. 팀 리뷰에서도
   나온 것이고, 위 다섯 곳 중 사용자가 실제로 막히는 유일한 자리다.
3. **주문표 만들기를 단계로 나눌지** — 맞바꿈이라 정하고 가야 한다. 2번을 하면
   "고치러 다시 들어오는" 흐름이 생기므로 그때 같이 보는 게 낫다.
