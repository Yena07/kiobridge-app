# 음성으로 프로필 만들기 — 지침

말로 주문표를 만든다. 백엔드가 음성을 글로 옮기고(STT), 그 글에서 우리 스키마에
맞는 값을 뽑는다(LLM).

이 문서는 **무엇을 만들 것인가보다 무엇을 하면 안 되는가**를 먼저 적는다. 이
기능은 이 앱에서 가장 위험한 자리다 — 사용자가 말하지 않은 조건이 주문표에
섞이면 그건 기능 결함이 아니라 **실격 사유**다.

> 화면이 "당신이 고른 조건을 이렇게 썼습니다" 라고 말할 때, 사용자가 실제로
> 고르지 않은 조건이 섞이면 안 됩니다.

---

## 0. 한 줄 요약

**모델은 값을 만들지 않는다. 우리가 아는 값 중에서 고르기만 한다.**
못 고르면 비워 둔다. 비운 것은 사용자에게 묻는다.

---

## 1. 이 기능이 건드리는 약속들

만들기 전에, 이 앱이 이미 화면에서 한 약속을 확인한다. 음성은 그 약속 중 셋을
직접 건드린다.

| 지금 화면이 하는 말 | 음성이 건드리는 지점 |
|---|---|
| "이름·전화번호는 받지 않아요" | **말에는 이름이 섞인다.** "저 김순자인데요" 를 그대로 받아 적으면 약속이 깨진다 |
| "이 기기 밖으로 나가지 않아요" (호칭) | **음성은 기기 밖으로 나간다.** STT 가 백엔드에 있으므로 |
| "이번 이용이 끝나면 남지 않아요" | 오디오·전사본이 서버에 남으면 거짓이 된다 |

세 번째가 가장 무겁다. **목소리는 그 자체로 개인을 식별할 수 있는 정보**다.
텍스트로 옮긴 뒤의 글보다 원본 오디오가 더 민감하다.

### 그래서 정한다

1. **오디오는 남기지 않는다.** 글로 옮기는 즉시 버린다. 디스크에 쓰지 않고,
   로그에 남기지 않는다.
2. **전사본도 남기지 않는다.** 값을 뽑고 나면 버린다. 화면에 보여 주는 동안만
   메모리에 있다.
3. **음성은 따로 동의를 받는다.** 지금의 개인정보 동의 한 칸으로 묶지 않는다 —
   기기 밖으로 나가는 것은 이것 하나뿐이라 같이 묶으면 동의의 뜻이 흐려진다.
4. **음성 없이도 다 된다.** 지금의 손으로 고르는 길을 그대로 둔다. 음성은
   **더해 주는 길**이지 대신하는 길이 아니다. 마이크가 없거나 안 되는 사람이
   막히면 접근성 기능이 접근을 막는 셈이 된다.

## 2. 흐름

```
 사용자          프론트                    백엔드                   OpenAI
   │
   │ "매운 닭강정 포장으로 두 개"
   ├──── 녹음 ───▶│
   │              ├─ 오디오 ─────────────▶│
   │              │                        ├─ STT ─▶ 글
   │              │                        │
   │              │                        ├─ 글 + 닫힌 목록 ────▶│
   │              │                        │◀─── 고른 값(JSON) ───┤
   │              │                        │
   │              │                        ├─ 우리 어휘인지 검사
   │              │◀── 뽑은 값 + 못 알아들은 축 ─┤
   │              │
   │◀─ 확인 화면 ─┤   "이렇게 이해했어요. 맞나요?"
   │
   ├─ 사용자가 고치거나 확인
   │              ├─ 그때서야 주문표로 저장
```

**저장은 사용자가 확인을 누른 뒤에만 일어난다.** 뽑은 값이 곧바로 주문표가 되면
안 된다.

## 3. 모델이 고를 수 있는 것 — 닫힌 목록

모델에게 **자유 텍스트를 만들게 하지 않는다.** 축마다 고를 수 있는 값을 그대로
주고, 그중 하나(또는 없음)만 고르게 한다.

닭강정집(`음식점`)의 축은 이렇다. `catalog.tsx` 의 `DETAIL_OPTIONS` 가 원본이고,
**이 문서에 값을 베껴 두지 않는다** — 두 곳에 적으면 언젠가 갈라진다. 프롬프트를
만들 때 코드에서 읽어 넣는다.

| 축 | 계약의 자리 | 못 골랐을 때 |
|---|---|---|
| 이용 방식 | `preferences.serviceType` | `NO_PREFERENCE` |
| 맵기 | `preferences.spicyLevel` | `NO_PREFERENCE` |
| 형태 | `preferences.boneType` | `NO_PREFERENCE` |
| 컵 | `preferences.cupOption` | `NO_PREFERENCE` |
| 수량 | `preferences.quantity` | `null` |
| 알레르기 | `hardConstraints.allergenIds` | `[]` — **아래 5번을 볼 것** |
| 가격 한도 | `hardConstraints.maxPriceKrw` | `null` |

### `NO_PREFERENCE` 와 `UNKNOWN` 을 뭉뚱그리지 않는다

```
NO_PREFERENCE   안 골랐다            → 서버가 알아서 고른다
UNKNOWN         골랐는데 우리가 모르는 값  → 서버가 주문을 막는다
```

음성에서 이 둘이 갈리는 자리가 분명하다.

- 말에 맵기 얘기가 아예 없었다 → `NO_PREFERENCE`
- "적당히 매콤하게" 라고 했는데 우리 목록(순한맛·보통맛·매운맛)에 딱 맞는 것이
  없다 → **`UNKNOWN` 으로 보내지 말고, 못 알아들은 축으로 표시해 사용자에게 묻는다**

두 번째가 중요하다. `UNKNOWN` 을 서버로 보내면 정규화가 `HARD_CONSTRAINT_UNKNOWN`
으로 막는다. 사용자는 왜 막혔는지 모른다. **모르면 서버에 묻지 말고 사람에게
묻는다.**

## 4. 프롬프트 규칙

백엔드가 OpenAI 를 부를 때 지킬 것.

### 반드시

1. **구조화된 출력을 강제한다.** JSON Schema(또는 function calling)로 축마다
   `enum` 을 박는다. 자유 문자열을 받아 우리가 파싱하는 방식은 쓰지 않는다 —
   모델이 "매콤한맛" 같은 없는 값을 지어낼 자리를 아예 없앤다.
2. **모든 축에 "안 말했음" 값을 둔다.** 모델이 빈칸을 채우려는 쪽으로 기울지
   않도록, 안 고르는 것도 정당한 선택지로 만든다.
3. **근거를 같이 받는다.** 축마다 "말의 어느 부분을 보고 골랐는지" 를 함께
   내게 한다. 근거가 전사본에 실제로 없으면 그 축은 버린다. 지어낸 값을 잡는
   가장 싼 그물이다.
4. **한 번에 한 주문표.** 여러 주문을 한 번에 말해도 나누지 않는다. 나누면
   무엇이 무엇에 붙는지 화면에서 설명할 수 없다.

### 하지 말 것

1. **추론하지 않는다.** "치킨 먹고 싶어" 에서 맵기를 짐작하지 않는다. "혼자
   먹을 거예요" 에서 수량 1을 만들지 않는다. 말하지 않은 것은 안 고른 것이다.
2. **바꿔 말하지 않는다.** 사용자의 말을 요약·정리해서 메모에 넣지 않는다.
   메모는 사용자가 적는 자리다.
3. **이름·전화번호·주소·주민등록번호를 어떤 칸에도 담지 않는다.** 말에 섞여
   들어와도 버린다. 이미 `개인정보같은메모()` 가 화면에서 하는 일을 여기서도
   한다.
4. **병원에서는 증상·진단·치료에 관한 말을 어느 칸에도 담지 않는다.**
   방문 유형(초진·재진·건강검진·검사)과 예약 여부만 받는다. 이건 선택이 아니라
   금지 사항이다.
5. **관공서에서 자격을 판단하지 않는다.** "제가 받을 수 있나요" 에 답하지 않고,
   그 말에서 어떤 값도 만들지 않는다.
6. **결제에 관한 어떤 값도 만들지 않는다.** 결제수단·카드·현금이 말에 나와도
   버린다. 이 앱은 장바구니까지만 한다.

## 5. 알레르기는 말로 받지 않는다

**이 문서가 제품보다 느슨했다.** 여기에는 "새우는 빼 주세요" 를 받으라고 적혀
있었는데, 실제로 만든 것은 **말로는 아예 안 받는** 쪽이다. 문서가 느슨한 채로
남으면 나중에 이것을 보고 만드는 사람이 느슨한 쪽으로 되돌린다 — 제품에
맞춘다(#99 리뷰).

알레르기는 **틀리면 사람이 다치는 값**이다. 서버에서 LLM 으로 뽑게 되더라도
이 축만은 말에서 뽑지 않는다.

### 규칙

1. **말에서 알레르기를 뽑지 않는다.** "새우는 빼 주세요" 도 받지 않는다.
   목록에 있는 값을 정확히 말했는지를 소리로 가리는 일 자체를 안 한다.
2. **눈으로 보고 고르게 한다.** 가입할 때 여섯 개를 화면에 놓고 고른다
   (`api/allergy.ts`). 잘못 들을 여지를 아예 안 만든다.
3. **안 들린 것은 '없음' 이 아니다.** 말에 안 나왔다고 "알레르기 없음" 으로
   확정하지 않는다. 이미 골라 둔 값이 있으면 그것을 쓰고, 없으면 없는 대로 둔다.
4. **모델이 알레르기 칸을 채워 주더라도 버린다.** 그 문은 프론트에도 하나 있어야
   한다(`api/voice.ts` 는 이 축을 아예 안 본다).

> 알레르기·품절·이용 불가 후보는 점수를 깎는 게 아니라 **후보에서 제거**한다.
> 눈으로 골라 둔 알레르기에도 똑같이 적용된다.

## 6. 확인 화면

뽑은 값을 그대로 저장하지 않는다. 사이에 화면이 하나 들어간다.

### 보여 줄 것

지금 화면이 실제로 쓰는 문구다. 문구의 원본은
[`VOICE_SPEAKING_GUIDE.md`](VOICE_SPEAKING_GUIDE.md) 이고, 여기서 베껴 적을 때는
그쪽과 글자까지 맞춘다 — 두 문서가 다른 말을 하면 어느 쪽이 화면인지 알 수 없다.

```text
이렇게 들었어요

“매운 닭강정 포장으로 두 개”

  [이용 방식 포장하기]  [맵기 매운맛]  [수량 2개]

못 들은 것 — 형태, 컵. 아래에서 골라 주세요.
말씀은 들었는데 어느 쪽인지 못 골랐어요 — 맵기. 아래에서 골라 주세요.

     [ 이대로 채우기 ]        [ 다시 말하기 ]
```

조사를 자리표시자로 붙이지 않는다. 받침에 따라 은/는이 갈리는데 코드가 그것을
정할 수 없어서 `"맵기은(는)"` 이 화면에 그대로 나왔다. 조사가 없어도 되는 문장을
쓴다 — 이 문장은 영어로도 나가므로 그쪽이 양쪽 다 깔끔하다.

**알레르기는 여기서 묻지 않는다.** 위 5번대로 말로 받지 않으므로, 확인 화면에도
알레르기 줄이 없다. 가입할 때 눈으로 보고 고른 값을 그대로 쓴다.

### 지킬 것

1. **말한 것과 안 말한 것을 구분해 보여 준다.** "안 정함" 을 빈칸으로 두면
   사용자는 우리가 뭘 골라 놨는지 모른 채 넘어간다.
2. **들은 대로를 같이 보여 준다.** 잘못 들었을 때 사용자가 그 사실을 알 수
   있어야 한다. 값만 보여 주면 왜 그렇게 됐는지 알 길이 없다.
3. **손으로 고치는 길을 항상 둔다.** 확인 화면에서 바로 지금의 만들기 화면으로
   갈 수 있어야 한다. 값도 그대로 물려준다.
4. **소리 안내를 켠 사람에게는 이 화면을 읽어 준다.** 이미 화면 전체를 읽는
   구조가 있으니(`speech.ts` 의 `화면글`) 따로 만들 것은 없다. 다만 이 화면은
   **읽기 전에 끊고 처음부터** 읽어야 한다 — 새로 뜬 줄만 읽으면 안 된다.

## 7. 안 될 때

음성은 자주 실패한다. 실패를 예외가 아니라 **정상 경로**로 다룬다.

| 무엇 | 화면이 할 일 |
|---|---|
| 마이크 권한 없음 | 음성 단추를 **아예 안 보여 준다**. 눌렀는데 아무 일도 안 일어나면 앱이 고장 난 것처럼 보인다. `소리를낼수있나()` 와 같은 판단이다 |
| 아무 말도 안 들림 | "잘 안 들렸어요. 다시 말씀해 주세요" — 몇 초 안에 답한다. 오래 기다리게 하지 않는다 |
| 글로는 옮겼는데 아무 축도 못 고름 | "무엇을 주문하실지 잘 못 알아들었어요. 손으로 골라 주시겠어요?" 하고 만들기 화면으로 |
| 일부만 알아들음 | 알아들은 것만 채우고 나머지는 "안 정함" 으로 확인 화면 |
| 서버가 안 됨 | 손으로 고르는 길로 보낸다. **음성이 안 된다고 주문표를 못 만들면 안 된다** |

**다시 시도 단추를 함부로 두지 않는다.** 같은 조건에서 다시 눌러 봐야 같은
결과다. 다시 말하게 하는 것과 손으로 고르게 하는 것 중 무엇이 나은지 화면이
판단해서 하나만 내민다.

## 8. 계약에 어떻게 실리나

음성으로 만들었다는 사실은 두 자리에 남는다.

```ts
interaction: {
  preferredInput: "VOICE",   // 소리로 말한 사람이다
  language: "ko-KR",
  confirmationRequired: true,
}
```

`source.collectionChannel` 은 `"WEB_FORM"` 그대로다. 계약이 그 값만 받는다 —
음성으로 받았어도 결국 웹 화면에서 확인을 거쳐 들어온 값이다.

`dataClassification` 은 `"SYNTHETIC_PROFILE"` 그대로다. **음성에서 뽑았다고
실제 개인정보가 되는 것이 아니다** — 오히려 그렇게 되지 않도록 4번의 금지
사항이 있다.

## 9. 백엔드에 요청할 응답 모양

프론트가 쓸 수 있으려면 이 셋이 필요하다.

```jsonc
{
  "transcript": "매운 닭강정 포장으로 두 개",   // 화면에 '들은 대로' 로 보여 준다
  "selections": {                              // 우리 어휘로 이미 옮겨진 값
    "맵기": ["매운맛"],
    "이용 방식": ["포장하기"],
    "수량": ["2개"]
  },
  "notHeard": ["형태", "컵", "알레르기"],       // 말에 없었던 축
  "unclear": [                                  // 말은 했는데 못 고른 축
    { "축": "맵기", "들은말": "적당히 매콤하게" }
  ]
}
```

- `selections` 는 **우리 화면이 쓰는 우리말 그대로**다. enum 으로 옮기는 것은
  `canonical.ts` 가 이미 하고 있고, 그 자리를 둘로 늘리지 않는다.
- `notHeard` 와 `unclear` 를 나눠 받는다. 화면이 둘을 다르게 말해야 한다 —
  전자는 "안 정함", 후자는 "이렇게 들었는데 못 알아들었어요".
- **상품 ID·좌표·후보 식별자는 어떤 칸에도 넣지 않는다**(P0-1). 의미값만 오간다.

## 10. 만들기 전에 답해야 할 것

아직 정해지지 않은 것들. 만들기 시작하기 전에 답이 있어야 한다.

1. **오디오가 OpenAI 를 거치나, STT 만 우리 서버에서 하나?** 거친다면 그 사실을
   개인정보 화면에 적어야 한다. 어디로 나가는지 안 적고 내보내면 안 된다.
2. **동의를 언제 받나?** 마이크를 처음 누를 때가 자연스럽다. 가입 때 미리 받으면
   쓰지도 않을 사람에게 동의를 받는 셈이다.
3. **얼마나 길게 녹음하나?** 길면 잘라 말하지 못하는 사람이 유리하지만, 오래
   기다리게 된다. 15초 안팎에서 시작해 보고 정한다.
4. **카페·병원·관공서도 지원하나?** 지금 백엔드가 다루는 것은 닭강정집뿐이다.
   음성도 거기부터 하고, 나머지는 축이 늘 때 같이 늘린다.

## 11. 이 기능이 다 됐다고 말하기 전에 확인할 것

- [ ] 말하지 않은 축이 채워진 적이 한 번도 없다 (근거 검사가 잡는다)
- [ ] "적당히 매콤하게" 가 `UNKNOWN` 으로 서버에 안 나간다
- [ ] 알레르기를 말 안 했을 때 "없음" 으로 확정되지 않는다
- [ ] 확인 화면을 거치지 않고 저장되는 길이 없다
- [ ] 오디오·전사본이 디스크와 로그 어디에도 안 남는다
- [ ] 마이크가 없는 기기에서 음성 단추가 안 보인다
- [ ] 서버가 죽어도 손으로 주문표를 만들 수 있다
- [ ] 이름·전화번호가 섞인 말에서 그 부분이 어느 칸에도 안 담긴다
- [ ] 병원에서 증상 관련 말이 어느 칸에도 안 담긴다
- [ ] 결제에 관한 말에서 아무 값도 안 만든다
- [ ] 확인 화면이 소리 안내로 처음부터 읽힌다
- [ ] `preferredInput` 이 `VOICE` 로 나간다
- [ ] `dataClassification` 이 `SYNTHETIC_PROFILE` 그대로다
